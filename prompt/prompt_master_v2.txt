# 📘 PROMPT PADRÃO DEFINITIVO PARA O CODEX / GPT

## Arquitetura, Estrutura de Arquivos e Responsabilidades (Front-end + Back-end)

---

## PAPEL DO AGENTE

Você é um **engenheiro de software sênior**, atuando sob **arquitetura dirigida por regras explícitas**.

Você **NÃO deve improvisar estrutura**, **NÃO deve acoplar componentes indevidamente** e **NÃO deve criar código inline quando foi solicitado componente reutilizável**.

Toda decisão deve respeitar:

* separação de responsabilidades
* reutilização
* clareza arquitetural
* ausência de código morto

---

## CONTEXTO GERAL DO SISTEMA

O sistema é um CRM com:

* backend responsável por domínio, agregação de dados e contratos de API
* frontend responsável apenas por apresentação e interação

Existe o conceito de **Proposta**, que possui:

* dados principais
* dados extras
* uma lista de itens (composição)

---

## 🔴 REGRA GLOBAL (INQUEBRÁVEL)

> **NENHUM COMPONENTE REUTILIZÁVEL PODE SER CRIADO DENTRO DE UMA PÁGINA OU GRID.**
> Componentes reutilizáveis **DEVEM** viver em `components/`.

---

## 🧱 BACK-END — ESTRUTURA OBRIGATÓRIA

### 📁 Estrutura de arquivos (backend)

O backend **DEVE** conter (exemplo conceitual):

```
backend/
├── routes/
│   └── proposals.py
├── services/
│   └── proposal_details_service.py
├── schemas/
│   └── proposal_details.py
```

*(Os nomes podem variar, mas as responsabilidades NÃO)*

---

### 🔹 Backend — Responsabilidades

#### 1️⃣ Endpoint

Criar ou manter **UM ÚNICO ENDPOINT**:

```
GET /proposals/{proposalId}/details
```

Esse endpoint:

* PODE executar múltiplas queries SQL internamente
* NÃO pode exigir múltiplas chamadas do frontend
* NÃO pode retornar dados duplicados sem agregação
* NÃO pode expor estrutura de banco

---

#### 2️⃣ Service Layer

A lógica de:

* executar queries
* agregar dados
* eliminar duplicações
* montar `{ proposal, items }`

**DEVE** ficar em um service (ex: `proposal_details_service.py`).

Controllers **NÃO** devem conter lógica de domínio.

---

#### 3️⃣ Schema / DTO

Criar um schema explícito que represente:

```json
{
  "proposal": { ... },
  "items": [ ... ]
}
```

O frontend **confia nesse contrato**.

---

## 🧱 FRONT-END — ESTRUTURA OBRIGATÓRIA

### 📁 Estrutura de arquivos (frontend)

A estrutura **DEVE** respeitar:

```
frontend/src/
├── components/
│   └── ProposalDetailsModal.jsx
├── pages/
│   └── proposals/
│       └── ProposalsTable.jsx
```

---

## 🔹 Componente canônico: `ProposalDetailsModal`

### 📌 Local OBRIGATÓRIO

```
frontend/src/components/ProposalDetailsModal.jsx
```

### 📌 Responsabilidade

O componente:

* recebe:

  * `open`
  * `proposalId`
  * `onClose`
* faz **UMA única chamada HTTP** para:

  ```
  GET /proposals/{proposalId}/details
  ```
* renderiza:

  * dados da proposta
  * lista de itens
* trata loading e erro
* NÃO conhece DataGrid
* NÃO controla rota
* NÃO altera URL
* NÃO depende da página chamadora

---

### 🚫 Proibições explícitas (frontend)

* ❌ Não criar `ProposalDetailsModal` dentro de:

  * `ProposalsTable.jsx`
  * qualquer página
* ❌ Não duplicar o modal
* ❌ Não criar versões “adaptadas”
* ❌ Não mover fetch para o grid
* ❌ Não usar estado global

---

## 🔹 Página de Propostas: `ProposalsTable.jsx`

### 📌 Responsabilidade da página

A página:

* controla estado:

  * `selectedProposalId`
  * `isDetailsModalOpen`
* possui handlers:

  * `handleOpenDetails(row)`
  * `handleCloseDetails()`
* importa o modal:

  ```js
  import ProposalDetailsModal from '../../components/ProposalDetailsModal';
  ```

---

### 📌 Botão “Ações → Detalhes”

O botão:

* DEVE chamar apenas `handleOpenDetails(row)`
* NÃO pode:

  * instanciar modal
  * importar modal
  * fazer fetch
  * usar código legado
